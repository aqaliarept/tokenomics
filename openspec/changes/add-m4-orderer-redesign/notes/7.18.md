# 7.18: `entity_planner_buyahead` (code, 2026-11-05)

## How `entity_planner` buys inputs today (domain/producer_planner.py `_plan_replenishments`)
- **The target.** Per input g: target = max(`input_stock_target` 3, `downstream_demand_pressure`
  + `blocked_reservation_qty`). It orders want = min(`max_replenish`, target − (inventory +
  outstanding inbound)).
- **The caps.** The inventory headroom (limit − held − inbound) caps the cycle's total, and so
  does the fund (`replenish_cost_per_unit`). Inputs are served by `input_value` priority (ties
  split evenly).
- **Feasibility.** Replenishment is not tied to reservations: a producer can already hold stock
  ahead of need (the floor of 3). So "order ahead" is feasible as worded; no proposal-first stop.
- **The holding penalty** (`env/aec_env.py` `R_HOLDING_PER_UNIT` 0.1 per unit, normalised per
  producer) is a training reward only. It does not enter the gate's consumer units; holding
  units are reported (`holding_units_per_cycle`).

## The rule (`eval/baselines.py`)
- **Recent input use:** `recent_input_use(view)` = Σ_x `recent_completed_qty`(x) × I[x, g].
  - `recent_completed_qty` is the telemetry EMA (α 0.3) of this producer's own completed units
    of x per cycle, folded at cycle end, so past cycles only.
  - Every completion consumes its inputs, so this is the EMA of its own input use. It is
    agent-local, with no same-cycle visibility (ADR-0058).
- **The target:** `buyahead_view(view, k)` raises each input row's demand pressure by ⌈k × use⌉,
  so the target becomes max(3, pressure + blocked + ⌈k × use⌉): k more cycles of its own use,
  ahead of demand. Headroom, the per-cycle ceiling and the fund gate are unchanged.
- **Everything else is `entity_planner`'s:** restoration, upgrade, inventory expansion and the
  input priority (scores) all come from the unmodified view.
- **k:** k = 1 registered (`entity_planner_buyahead`), k = 2 reported
  (`entity_planner_buyahead_k2`). k = 0 is `entity_planner` exactly.
- **`domain/` untouched.**

## Deviation: not in `PRODUCING_BASELINES`
- **Why.** The roster drafts v1–v3 cross every `PRODUCING_BASELINES` entry (`roster._cross`). A
  new entry there would change those drafts and the frozen gate sets screened on them, a
  human gate.
- **What instead.**
  - The two producers live in `baselines.EXTRA_PRODUCING`.
  - `baselines.producing_policy(name)` resolves both dicts, and `decoder_check.decoder_policies`
    (the job path of decoder_check / split_need / supply_trace) uses it. Same policy objects
    for existing names.
  - Adding the producers to a roster is a later human decision (the "roster holds the strongest
    policy" rule, after 7.19).
