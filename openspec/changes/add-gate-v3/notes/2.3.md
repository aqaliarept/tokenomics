## What changed

### `/srv/research/tokenomics/tokenomics/tokenomics/eval/gate.py`

**`SideEffectParams`**
- New field `families: tuple[(family, X, Y), ...] | None`.
- From parameter version 3 (`FAMILY_PARAMS_VERSION`), `families` is required and `x` / `y` are
  None.
- Below v3 the scalar `x` / `y` are required and `families` is refused.
- `values_for(family)` returns the scalar pair for v1 / v2 whatever the family. From v3 it returns
  the family's pair, refused if the file has none for that family.
- `missing_families(families)` lists the families the file has no values for.
- `per_family` is a property that is true from v3.

**v3 parameter file**
- Fields: `{name, families, q, rule, method, evidence, screened_on}`. `families` is
  `{family: {x, y, evidence}}`.
- The family evidence holds `episodes`, `run_down_values`, `fill_values`, `rows_digest` and
  `bests_digest` (v2's evidence, per family), plus `run_down_distinct`, `fill_distinct`,
  `x_is_minimum`, `y_is_minimum` and `small_sample`.
- Written by `side_effect_params_payload_v3` / `side_effect_params_json_v3`.
- `params_from_dict` is version-aware:
  - v1 / v2 parse exactly as before;
  - v3+ refuses malformed families and evidence;
  - v3+ refuses a `small_sample` flag that does not follow from the distinct counts.

**Calibration**
- `calibrate_x_y` is now a thin wrapper around a shared `_calibrate`. Its output is
  byte-identical: EXP-0047's frozen files still re-derive, see Verification.
- New `FamilyCalibration` and `calibrate_families(rows, roster, q, world_family)`.
  - It applies v2's nearest-rank rule to each family's rows alone, pooled over sizes, so
    sparse_wide's 12- and 42-producer episodes form one sample.
  - It records distinct counts on the value lists, which is what makes triplicated calm values
    count once.
  - It records whether each quantile is the sample minimum, and `small_sample`.
  - It refuses rows of worlds that have no family, so excluded or replaced worlds cannot slip
    into a sample.

**`compute_report(..., world_family=None)`**
- v1 / v2 parameters: unchanged, one X and Y for every world and per-row checks.
- v3+ parameters:
  - `world_family` is required, must cover every judged world, and the file must have every
    family present. Otherwise the report is refused.
  - Each world uses its family's X / Y.
  - Each candidate episode goes through `_replicated_failures`:
    - **deaths** are checked per replicate, and each dead replicate is a failure naming
      (world, episode, replicate);
    - **run-down** is judged on the replicate mean of r_end / r_start over replicates with
      r_start > 0. That is the statistic `episode_bests` calibrates X on;
    - **starvation** is judged per consumer on the replicate mean of its fill rate, over the
      replicates where it ordered. That is the statistic Y is calibrated on;
    - the per-replicate run-down and starvation failures the v1 / v2 rule would record go to
      `GateReport.replicate_violations` and `WorldResult.replicate_violations`. They are
      monitored, never gating.
- `recompute_from_csv` passes `world_family` through.

**Report fields**
- New optional fields, emitted only when set, i.e. under v3+ parameters:
  - `WorldResult.family` and `WorldResult.replicate_violations`;
  - `GateReport.families` and `GateReport.replicate_violations`.
- `GateReport.x` / `y` are None under v3; the applied pairs are in `families`.
- A v1 / v2 report's `to_dict` / JSON, and its `worlds.csv` columns, are unchanged.
- `_episode_failures` now takes (x, y) instead of the params object. Its arithmetic is unchanged.

## Departures from the task text / sources (each for the reviewer)

1. **`gate_cli.py` is edited, although tasks.md places 2.3 in `gate.py`.**
   - "The run-down and starvation checks use the world's family" needs each world's family at
     report and recompute time. Rows carry no family, and recompute reads only `spec.json`, so the
     family is pinned in the grid. That pin is written only under v3+ parameters, which keeps
     v1 / v2 pins, resume checks and recomputes unchanged.
   - "A v3 file missing a family present in the registry is refused" needs the registry, which
     the pure `gate.py` does not import (registry imports gate). The check therefore lives in
     `gate_cli.params_family_problem` and `run_report`.
   - `compute_report` also refuses a missing family among the judged worlds, as a pure backstop.
2. **"Missing family" means a non-excluded family.** A family × size excluded at screen (D3
   step 4) has no X / Y by construction, since excluded rows enter no X / Y. So families whose
   every entry is `excluded` are not required. A family with an admitted size is still required.
3. **`small_sample` reads both quantities.** D4 / the task say "< 20 distinct values" without
   saying of what. I flag when **either** the run-down or the fill distinct count is below 20, and
   record both counts. Using only run-down would hide a thin fill sample.
4. **The screen's per-family calibration is not wired.** `calibrate_families` and the v3 file
   writer are provided, but `screen_outcome` still writes v1 / v2 scalar files. tasks.md 3.1 owns
   the v3 screen ("Output. Per-family X / Y (2.3)"), and wiring it here would change 3.1's
   surface early.
   - "sparse_wide ... recomputed with the v3 roster" happens when 3.1 calls `calibrate_families`
     with the v3 roster and the admitted final worlds. Nothing here recomputes it.
5. **Run-down fail-closed rule under replicates.** v1 / v2 fail a row whose r_start or r_end is
   None. Under v3 an episode fails as unmeasurable if **any** replicate has a None, which keeps
   fail-closed, rather than averaging over the measurable replicates. The calibration skips such
   replicates, but a lenient check would let an unmeasurable replicate hide.
   - With every r_start 0 there is no ratio, and the check passes, matching v1 / v2's
     r_end ≥ X·0.
6. **Per-replicate violations are listed for every v3 candidate, including R = 1.** For a
   deterministic candidate they duplicate the gating failures. I kept one rule for all R rather
   than special-casing R = 1. They are labelled monitored.
7. **The EXP-0047 "recompute" is a screen re-derivation.** EXP-0047 is a screen: it has no
   `verdict.json`, so `--mode recompute` cannot run on it. The test re-derives its three frozen
   files from its `episodes.csv` through the pure `screen_outcome` and compares them byte for
   byte. EXP-0045, the only recorded gate report and a v1 one, recomputes to MATCH through
   `recompute_details`, and I also ran it through the CLI.
8. **Carry-forward (1.1, binding) `RANDOM_POLICY in pair` → `roster.is_stochastic(*pair)`: not
   done here.**
   - The carry-forward assigns it to "Task 3.x / 4.x … before any read with a baseline subject".
   - 2.3's checks are pure arithmetic over whatever candidate replicates the rows hold. How many
     replicates a subject runs is a job-planning decision in `gate_cli.build_jobs` and the
     `candidate_replicates` pin, which 4.1 (`--subject per-order`, R = roster R) reworks.
   - So it stays open for 3.x / 4.x as recorded.

## Review round 1 (2 test-gap concerns, both fixed)

1. **The v3 replicate-mean checks had no equality-boundary test.** The reviewer's B1 (starvation
   fails at a mean ≤ Y) and B2 (run-down fails at a mean ≤ X) survived. The new test
   `test_v3_replicate_means_exactly_at_the_bar_pass` uses values that are exact in binary floating
   point. Each case below passes:
   - fills 0.25 and 0.25, mean 0.25 = Y;
   - fills 0.125 and 0.375, mean 0.25 = Y, with the 0.125 replicate monitored;
   - ratios 0.25 and 0.75, mean 0.5 = X;
   - a single replicate with ratio 0.25 / 0.5 = X.
2. **No test pinned "the statistic the calibration uses".**
   - `test_v3_run_down_is_the_mean_of_ratios_the_calibration_uses` has replicates with
     different r_start, in both directions:
     - ratios 0.25 and 1.0: the mean of ratios is 0.625 and passes, while the ratio of means
       would be 0.4;
     - ratios 0.875 and 0.0625: the mean of ratios is 0.46875 and fails with that value, while
       the ratio of means would be about 0.785.
     - The same replicates (plus one at 0.46875), as the per-episode argmax random member, reduce
       in `episode_bests` to `run_down` 0.46875 and to fill mean 0.375, with c1's None skipped.
       So the check and the calibration read one statistic.
   - `test_v3_starvation_skips_replicates_where_the_consumer_did_not_order`:
     - fill 0.375 with a None passes; counting the None as 0 would give 0.1875 and fail;
     - fills 0.125, None, 0.125 fail at 0.125; counting the None as 0 would give 0.083;
     - None in every replicate is not judged.
