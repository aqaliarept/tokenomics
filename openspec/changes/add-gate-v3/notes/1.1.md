## Gotchas for 1.2 / 2.x / 3.1

- **`gate_cli` candidate path (3.x / D6).** `build_jobs` (baseline subject) and the
  `candidate_replicates` pin (~l. 747) still use `RANDOM_POLICY in pair`. A
  `--subject baseline:entity_planner/makeable_weighted_whole` would run 1 replicate with no
  replicate seed. Switch both to `roster.is_stochastic(*pair)` when 3.x touches `gate_cli`. Roster
  members are already correct (`m.random`).
- **Pilot roster in a real screen.** The pilot carries version tag 3, so a v3 registry does not
  refuse it on the tag check. 3.1 should refuse `PILOT_V3_NAME` outside `--dry-run`. A dry run with
  member filters renames it "<name>-dry-run".
- **`STOCHASTIC_BASELINES` drives `Roster.validate`.** A roster file whose member flags disagree is
  refused. 3.1's two-wave plan and pruning record should keep using `m.random` /
  `replicates_for`, never `RANDOM_POLICY`.
- **`routing_audit.ordering_policy`** now resolves the five names from `ORDERING_BASELINES`. These
  are the same objects, so nothing changes. `atlas` / `routing_audit` `router_table` derive a roster
  member's kind from `m.random`, which is correct for v3 rosters.
- **Ceiling tests.** `tests/test_ceiling_bound*.py` parametrize over
  `[*ORDERING_BASELINES, "round_robin"]`, so `round_robin` now appears twice. This is harmless,
  but it costs a little extra runtime.
- **M4 fingerprints.** The new file and the edits change the package source hash and
  `teacher_path_fingerprint`, which covers every package `.py` file. Land this commit between M4
  pod runs (tasks.md coordination note).
- **For 1.2 (ADR).** Cite the module split (D1 "No import cycle") and the `is_stochastic` rule. The
  stored field keeps the name `random` for hash stability.
