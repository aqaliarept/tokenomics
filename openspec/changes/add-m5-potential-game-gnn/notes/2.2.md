# 2.2: ES driver (`train/producer_es.py`)

## Decision record (supervisor, 2026-11-05, before any 2.2 code)
- **Fitness is consumer units only,** relative to the bar (the base rf3 + MWWk on the same
  world-episode and draw key), with no holding term. This is design D3 ("scores whole-episode
  consumer units directly"), and it matches what the gate measures. M4's `order_es` fitness
  subtracted h · H (h 0.1); that term is not used here.
- **Guard:** the run-down / starvation disqualification stays as designed (D5), relative to rf3,
  with its margin measured on rf3's own re-keyed replays (L1).
- **Diagnostics in every generation and every read:** holding units per cycle and the investment
  rejection rate, for the members and the base. Reported, never in the fitness or a reading.
- **Registered sanity check `stock_heavy`** (in the pre-registration, task 2.3):
  - flagged when the selected θ's mean held stock (holding units per cycle) exceeds rf3's by more
    than 50% on the read's world-episodes;
  - reported only, never deciding;
  - the supervisor takes a flag to the user, since the domain treats carried inventory as a
    liability.

## Decision record (supervisor, 2026-11-05): the training set
- **Option 1:** reuse M4's pinned training set and schedule. That is EXP-0058 `bar/`: 64 worlds at
  12 producers, the 23 loaded atlas v2 train worlds plus 41 fresh world-space draws, 128
  world-episodes with fresh episode seeds, the 16-world-episode monitor set, the minibatches per
  optimiser seed, and the probe's two minibatches.
- **Why:**
  - the pool size minibatch 24 and a 16-episode monitor need (DIAGNOSTICS 25 / 27);
  - validation / held-out splits disjoint by construction;
  - no reuse of the EXP-0057 world-episodes that selected rf3.
- **L1 (task 4.1)** builds a new rf3 + MWWk bar on those 128 world-episodes. Its check:
  - r0 reproduces the bar's rf3 rows;
  - rf3 replayed on 2 EXP-0057 world-episodes equals EXP-0079's rows (it ties the code path to
    EXP-0079).
- **Design D7 and task 4.1** were updated accordingly.

## Implemented (2026-11-05)
`train/producer_es.py` (driver `python -m tokenomics.train.producer_es --mode
bar|noise-floor|probe|train`).
- **Reuse:**
  - `order_es`: the ES math (`noise`, `member_thetas`, `rank_and_estimate`, `AdamState` /
    `adam_ascend`, `cosine`) and the guard (`read_bar`, `disqualifying`, `score_member` with
    h = 0, `noise_margins`, `self_flags`, `a0_values`), imported lazily;
  - `order_es_worlds`: the training set (`Candidate`, `monitor_set`, `minibatch`,
    `probe_minibatches`, `content_hash`).
  - The worker imports only `eval/` and the residual, so spawned workers do not load the orderer
    stack.
- **Jobs:** the producer under test (rf3 for the bar / noise floor, the residual θ for probe /
  train / monitor) with `mww_keyed` at DrawKey(world, episode, replicate), joint_stack. Rows are
  the gate row format plus ES columns. Every row is checked against the bar's demand / shock digests.
- **`bar`:** rf3 at r0 on the 128 training world-episodes → `bar.csv` (order_es's format; B_we =
  rf3's units) and `base_rows.csv`. A real run also needs `--atlas` and `--exp0079-episodes`: rf3 is
  replayed through `supply_trace.run_supply_job` on the first 2 EXP-0079 MWWk r0 world-episodes, and
  every cell must equal EXP-0079's (`crosscheck.csv`).
- **`noise-floor`:** rf3 at r0 + r1..r4. r0 must reproduce `base_rows.csv` (`reproduction.csv`).
  The margin is c · √2 · pooled SD (c = 2, order_es's formula), with rf3's self-flags against its r0
  (target ≤ 5%) → `margins.json`.
- **`probe`:** M4's recorded probe stream at size 24 (two disjoint minibatches) and one common
  noise draw at θ = 0. The ES estimate per minibatch (ranks; a disqualified member ranks worst)
  gives a cosine → `signal` ≥ 0.3 / `weak` ≥ 0.1 / `no_signal` (`probe.json`).
- **`train`:**
  - generation g's minibatch is M4's recorded stream for the optimiser seed (`ow.minibatch`;
    checked against `schedule.json` where its size matches);
  - 2 × PAIRS members, centered ranks, Adam (order_es's lr 0.02, weight decay 0.005);
  - a checkpoint per generation; resume continues from the latest one under the same pins, and
    the target may grow (pilot 20 → main 40);
  - other pins are refused;
  - the monitor every 10 generations: the centre θ on the 16 monitor world-episodes,
    g_tr = mean(units − the bar's rf3 units);
  - diagnostics in `generations.csv` / `monitor.csv`: holding units per cycle and the investment
    rejection rate (members and bar), never in the fitness.
- **Placeholders for 2.3:** PAIRS 12, MINIBATCH 24, σ 0.1, lr 0.02, generations 20 / 40, monitor
  every 10, probe thresholds 0.3 / 0.1, self-flag target 5%. 2.3 freezes them; a real probe / train
  run will then need the pinned pre-registration.
- **Real runs** need a 40-hex commit, horizon 100 and no filters. A dry run restricts the training
  set to its bar's world-episodes.

## Review m5-2-2 fixes
1. **Monitor and resume.** The monitor is one function. A resume first runs a monitor that is
   missing for the checkpoint's generation (the run died after the checkpoint, inside the monitor).
   - `generations.csv` keeps one row per generation and drops rows beyond the checkpoint (a crash
     between the row and the checkpoint).
   - The run cannot end `complete` with a due monitor missing.
   - A monitor with missing rows raises.
2. **Real runs and the pre-registration.** Real probe and train runs are refused until task 2.3
   pins `train/registry/es_prereg_m5_v1.json` (`PREREG_SHA256` None until then; a file whose SHA
   differs is refused too). `--monitor-every` other than 10 is a refused filter in a real train run.
   These checks run before the bar-coverage check.
- **Tests** (test_producer_es, 10 passed): a crash inside generation 2's monitor, after its
  checkpoint, leads to a resume that writes that monitor (θ of gen-002); a generation row without
  its checkpoint is not duplicated; real probe / train are refused without the pre-registration;
  `--monitor-every 7` is refused.
