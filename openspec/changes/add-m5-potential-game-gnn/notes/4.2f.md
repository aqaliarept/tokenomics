# 4.2f: rf4, rf3 plus the sustainable-upgrade cap (2026-11-05)

**User decision:** "Fix the base, test widely" (notes/user-decisions.md), after 4.2e / DIAGNOSTICS 29.

**Supervisor decisions (2026-11-05, before building):**
1. **View only.** The degradation percentage is not in the producer's view; the per-cycle degradation
   `ceil(d% · max / 100)` is. The post-upgrade degradation is estimated as
   `ceil(degradation · (max + upgrade_effect) / max)`, which is never below the exact value. An upgrade is
   blocked when that estimate exceeds `restore_effect`. No domain change.
2. **No cap when `restore_effect` = 0** (the restoration targets another type). Degradation stays
   proportional to max, so an upgrade barely changes such a type's time to zero, and a cap adds nothing.

**Build:**
- `eval/baselines.py`: `over_sustainable_max(view)`, plus `producing_entity_planner_buyahead_rf(...,
  upgrade_cap=True)`.
  - When the plan chose an upgrade and the cap fires, the upgrade is dropped and the rest of the command is
    rf3's. The budget is not re-spent, as in 4.2e's veto.
  - Blocks are counted per system in `policy.upgrades_blocked`.
- The `EXTRA_PRODUCING` entry is `entity_planner_buyahead_k4_rf4`. rf3, k4 and `entity_planner` are unchanged.
- `eval/supply_trace.py` gets a trailing `upgrades_blocked` column ("" for producers without a cap).

**Tests (`test_buyahead`):**
- The cap blocks 12-0016's p0_0 case (263 → 271: 17 > 16) and allows 200 → 208. It does not fire without an
  upgrade or with `restore_effect` = 0.
- rf4 equals rf3, action for action, on atlas 12-0111 (no over-ceiling upgrade wanted).
- On atlas 12-0121 (horizon 40) rf4 equals rf3 up to its first block and differs there.
